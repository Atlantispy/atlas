# Prepared construction and explicit restart bindings

WORKING NON-CANON. These construction tools prepare source and profile metadata.
Construction, receiving qualification, native publication and independent cold
reopening, scientific acceptance and publication of source are separate states.
The long positive native publication/reopen validation remains held.

## Produce the selected source generation

The retained assembler calls `private_heat_bundle.construct_successor`, retaining
the legacy indexed-heat route and all exact transform assertions. It does not
select the compact constructor. An authenticated source map supplies every
input; each transform's measured output must match its separately selected
stage digest. Measuring stages produces evidence rather than a buildable
composition. Construction with unchecked stages refuses.

The preparer emits an exact source-copy plan. Its stager authenticates metadata,
source membership, byte identities, allowed parent directories, path topology
and size bounds before creating an exclusive destination. It preserves partial
outputs after failures and refuses an existing generation. A new selection
requires a new generation rather than alteration of historical source or receipts.

Every new prepared runtime manifest explicitly declares
`completed_query_store: "files"`. Receiving manifests must declare that same
selected disposition. Missing, malformed or unknown declarations refuse.
Declaring `columnar` does not authorise conversion to files or a silent fallback;
it requires a separate source-bound selection and compatible runtime.

## Generate the v2 profile through the actual writer

The assembler's `write_review` and the pinned `write_prepared_profile.py` entry
emit `atlas.prepared-restart-launch.v2`. The closed record includes an explicit
workspace-relative `historical_root`, its historical native source root, native
and helper import roots, complete module bindings, preparation and driver pins,
the source manifest and compatibility policy, store settings, query quotas and
fresh attempt paths. It grants no run authority.

The historical root must name the reviewed tree within the workspace. Both it
and its source root must exist, resolve to the required relative layout and be
reached without symbolic links or Windows reparse points. No parent search,
default root or source-path guess is used. The producer and independent reader
consume the same pinned profile; changing profile bytes invalidates that binding.

The writer authenticates all declared source and data bytes and the complete
native Python inventory before creating profile output. The runner's
`RestartProfile` and `RestartSources` independently consume those bindings.
The monitored launcher checks profile, manifest and runner pins before executing
the runner. Its command inspection alone does not prove historical admission:
the runner and reader separately call the explicit historical-root checker.

The files-store declaration reaches `query_store_arguments`. File-only owners
retain their supported arguments. A declared columnar store requires the selected
storage parameters and flush support; absence of those capabilities refuses
before work. Existing stage-count, flush-before-count and failure-recording
behaviour remains in the selected runner rather than a competing helper.

## Connect a shared construction result

The same assembler and writer also accept a pinned selected-construction record
through `--selected-restart`. That closed input binds the construction receipt,
derivation, composition, actual emitted constructor profile, compatibility policy
and complete v2 profile fields.
The constructor supplies exact paths and identities; this consumer discovers
none and changes no source tree.

The explicit ordinary constructor receipt may reside in the separate owner
workspace. Runtime records remain contained in the profile workspace. In native-only mode, the actual emitted constructor profile is authenticated
against both recorded profile digests and already uses v2. Supplied restart
bindings match every field. Paired mode retains its fresh-v1 primary and separately
binds its actual prepared-v2 companion, as described below. Neither mode converts
the primary schema or rewrites a profile field.
Exclusive profile output preserves the emitted bytes and digest.

Receipt and derivation must both declare `PREPARED_SOURCE_NOT_QUALIFIED` and
neither may contain a `purpose` key. Presence refuses even when its value is
null, an empty string, false or zero. Literal purpose keys at every nested dictionary depth refuse, including within
lists. Dictionary keys or string values beginning `plan31:rehearsal-` after
casefold also refuse across receipt, derivation, composition, selection, reviewed
inputs, manifest and profile. A rehearsal cannot become an admissible source
merely by carrying an otherwise allowed status. Matching construction identities,
reviewed-input/bootstrap pins and completed construction finality are required.

All checks precede exclusive profile creation beside the selected runtime
manifest. The actual constructor/writer/source/profile checks and real public
receiving loader exercise this component boundary together. The shared constructor
owns its final materialisation and bindings. Individual-plan verification after
full assembly is cancelled by the owner; no extra Plan02 return or sign-off is
required. Cancellation does not create native or scientific acceptance.

## Evidence and limits

Disposable controls exercise generated v2 profiles through the selected runner,
reader binding and monitored-launcher loader, and through both writer entry
points. Negative controls cover missing and incompatible store declarations,
purpose presence, rehearsal records, omitted and foreign roots, an injected
reparse attribute, incorrect pins, changed source and additional native members.
They check nonzero refusal and absence of output. The reparse injection is a
synthetic fault control, not a claim that a real junction was tested.

Existing by-need admission retains integer `P + ceil(P/5) + 2 GiB`, qualifying
measured records, paired explicit booking arguments and seed-zero child checks.
Refusal precedes run outputs, and stop-before-advance remains root-only.
Initial and evolved collar metadata retain the paired heat/transport identities.

These controls establish bounded source/profile behaviour. They establish no
native publication, independent cold reopen, interval result or scientific
acceptance. Historical checks remain valid only for their exact source bindings;
they do not automatically qualify a changed final runner/reader pair. Known
capacity-layout errors remain named limitations rather than passing tests.

Private manifests, source-copy inputs, runtime profiles, checkpoints, receipts,
logs and coordination records are excluded from the public source snapshot.
Public source identities do not authenticate private historical execution.


## A runtime with both fresh and prepared consumers

The final source/runtime pair retains fresh-profile.json with the fresh-v1 schema
and its fresh_interval_driver. A separate prepared-profile.json uses prepared-v2
and prepared_interval_driver. The primary profile_sha256 in construction receipt
and derivation keeps its fresh meaning. Both records independently bind the actual
prepared companion with the same explicit prepared_profile path and digest.

The closed paired receiving input additionally identifies the fresh and prepared
runner files and the prepared companion. Constructor_profile is the actual fresh
primary; profile fields describe the already emitted prepared companion. The
consumer authenticates both actual files, their records and manifest-bound runner
bytes, then checks each complete module map against the selected runner's literal
contract. Shared source roots/manifest and intersecting module names agree; the
drivers stay distinct, connected through the explicit prepared driver binding.
Per-leg output/query destinations and valid quotas remain explicit.

There is no implicit profile conversion or copied/relabelled construction receipt.
The existing writer emits the exact prepared companion bytes and digest. All
eight generation documents, including both profiles, undergo recursive purpose
and casefolded rehearsal-marker refusal. The authenticated inherited staged.root
absolute string is retained as historical metadata; actual staged records still
require objects and no historical directory is discovered or imported from it.

Construction ordering is source/composition/manifest, then both profiles, then
derivation/receipt and finally the generated receiving configuration. Profiles
never enter their own source manifest: that would introduce a hash cycle. The
construction owner selects/materialises exact paths and returns actual bindings
and receiver evidence. Source candidate checks do not establish that final seam.

Fresh profile manifest paths retain workspace-relative spelling; its query directory sits outside its attempt and has an ordinary existing parent. Construction-record absolute references retain their separate explicit contract.
