# Folded runtime metadata construction

This guarded tool derives a new runtime manifest and paired profiles from one authenticated, completed fold. Its output remains `PREPARED_SOURCE_NOT_QUALIFIED`. Source construction, strict identity capture, receiving qualification, Release admission and scientific acceptance are distinct outcomes.

`build_folded_runtime.py` retains the r3 constructor logic and binds the selected fold and parity hashes to their explicit tool successors. The five logical report-role keys stay fixed; the parent fold, facade, fixture and capture identities are unchanged by the checker and derived-pin fold binding update. When it derives the manifest, the constructor compares an exactly empty `by_path` in the fold's fixture declaration as absent, as the fixture reader does; a non-empty one must still match exactly. A checker source qualification does not establish complete fold or runtime qualification. `capture_folded_identity.py` is the print-only capture adapter with LF line endings; its implementation is unchanged. All source records, component paths, the interpreter, accepted evidence and output coordinates are supplied externally by the caller; this directory contains no native payload or runnable default configuration.

## Actual connected route

1. Authenticate the completed source construction receipt, its complete original source bindings, composition, manifest, fresh/prepared profiles and compatibility policy. Authenticate the completed fold's exact mapping, members and five fixed tool-role pins. Its seven gate keys must be exactly `ast`, `placement`, `historical_root`, `pins`, `scan`, `k3` and `placement_after_probes`, each with `PASS` or `PRIVATE` status. The report must contain `rehearsal` as an actual empty JSON list. Missing, null, boolean false, nonempty lists and other types are refused. The actual Plan26 caller separately requires all seven gates to PASS and refuses PRIVATE for final fold qualification.
2. Derive a new manifest from the actual folded membership and translations. Produce a fresh profile whose native/import roots and 21 logical module bindings select the folded package. Preserve unchanged scientific settings, historical inputs and external dependencies; relocate only owned runtime I/O into the explicitly selected new runtime root.
3. Emit that manifest and fresh profile, then launch the pinned capture adapter in a fresh, pinned interpreter with `-B -s -P`. The adapter authenticates the folded bootstrap and runners, calls the checked installed loader, enters the actual `FreshSources.selected()` lifetime and creates a strict `ExecutionContext` with the SciPy backend. It checks source/import boundaries, closes the context and returns matching before/after source proofs and the measured execution identity. It dispatches no worker and writes no policy.
4. Build a new compatibility policy from that measured identity and the exact reviewed historical-to-folded source delta. Authenticate the fixed prepared component and its historical-input sibling. Call its real `build_restart_profile` producer through `build_prepared_profile`, requiring the result to equal the intended 41-module prepared profile in every field. Emit the prepared profile and final construction result only after input/output finality checks.
5. Use the emitted manifest and new paired profiles in the actual receiving and final consumer routes. The constructor is connected to those real APIs; adding these helpers alone does not complete integration. Actual construction/capture, receiving checks and consumer use remain owner work, followed by the required final acceptance and publication.

The original manifest's `composition` is deep-copied unchanged. Its original composition file remains pinned DATA: it records source-generation lineage and the existing production gate's strict-peak lookup key. Folded native identity is recorded separately by the complete folded `source_hashes` and actual strict capture. Retaining lineage grants no measured peak, production or scientific admission; missing authentic peak tables continue to refuse through the unchanged gate.

The source-stage c697 high-level paired intake is already evidenced on its actual original configuration. It is not rerun on folded metadata, and there is no new post-fold `selected_restart_profile` prerequisite, invented intake PASS or receipt bridge. An optional `review.evidence` entry named `source-paired-intake.json` lets the constructor authenticate and retain that original observation; without it the generic constructor does not reassert the earlier disposition. Actual folded `build_restart_profile` producer validation is reported separately.

## Caller contract and apply binding

Every source reference has exactly `path` and lowercase raw-byte `sha256`. The closed `atlas.plan31.folded-runtime-context.v2` record contains:

- `constructor`; canonical absolute `workspace`; relative `source_root` and `folded_root`;
- `sources`: `construction_receipt`, `composition`, `manifest`, `fresh_profile`, `prepared_profile`, `policy`;
- `fold`: actual `manifest`, `report`, `proof`, accepted `tool` and `tool_acceptance`;
- `components`: fixed accepted `utility`, `support`, `prepared_component`, `capture` roles and the actual pinned `interpreter`;
- `destinations`: a separately pinned `atlas.plan31.folded-runtime-destinations.v1` record containing `workspace`, `source_root`, `folded_root`, `source_composition`, `fold_manifest`, `runtime_root` and `evidence_root`;
- `review`: `changes`, covering exactly every changed/added/removed native source, and `evidence`, mapping safe single filenames to pinned records;
- `capture_timeout_seconds`: an explicit integer from 1 to 3600.

The constructor's accepted compiler/capture and fold-tool role hashes are fixed in code; mutable context hashes cannot select different executable roles. The capture component must reside outside the selected native workspace. The source receipt must be complete and source-only, with authentic generation/stage/raw bindings, empty pending work, true input/output finality and false execution, interval, hold-release, scientific, default-change and numerical-change flags.

Use the caller-selected pinned interpreter in place of `PINNED_PYTHON` and actual operands in place of the uppercase placeholders:

```text
PINNED_PYTHON -B -s -P build_folded_runtime.py plan --context CONTEXT_JSON --context-sha256 CONTEXT_SHA256
PINNED_PYTHON -B -s -P build_folded_runtime.py apply --context CONTEXT_JSON --context-sha256 CONTEXT_SHA256 --reviewed-constructor-sha256 bb9d900996c7224240f42473b75af47024e6bba65b8fb2fd948b10ec3c5b03d9
```

`plan` reads pinned inputs and derives metadata in memory without creating destinations; its ready result is not apply authority. `apply` requires the separate independently reviewed constructor pin from the implementation handoff. It must equal both the actual constructor bytes and the context binding. The exact candidate pin shown above does not itself assert reviewer acceptance. Implementation review is required before integration; tests are supporting evidence and require no separate reviewer gate.

The caller must choose absent, disjoint runtime/evidence roots with ordinary parents, outside all input roots. Before writing and again at apply, the constructor checks every planned metadata/evidence/failure file, owned attempt/store/query directory and owned ancestor for absence, containment, case-insensitive uniqueness, file/directory collisions and input/output separation. Each planned path's UTF-16 length plus 8 must be strictly below 260. Existing and failed destinations are preserved; choose new destinations for a later attempt.

Expected runtime files are `manifest.json`, `fresh-profile.json`, `runtime-policy.json` and `prepared-profile.json`. The separate evidence root retains selected proof copies, `capture-request.json`, `capture-process.json`, `capture-result.json` and the last-written `construction-result.json`; failed work retains `failure.json` when its evidence root exists. The constructor makes no native-source edits, creates no stores and grants no worker, interval, Release, default-enablement or scientific authority. Successful strict capture is identity evidence, not final qualification.

## Retained check scope

The r3 constructor has 32 metadata controls; the capture adapter has 20 inert/refusal controls. That evidence is retained across the capture helper's line-ending normalisation and corresponding constructor pin update; focused pin checks cover the publication bytes. The fold-binding update adds inert controls that run the exact `fold_maps` definition with the selected fold-tool roles and the exact `map_manifest` definition on the actual selected fold MANIFEST. A separate check authenticates the original source-stage intake bindings. Those checks did not construct the actual fold/runtime, create an actual execution context, dispatch a worker or qualify installed delivery. Candidate syntax/help/privacy checks add no runtime claim. Actual fold proof, construction, strict capture and receiving/final-consumer evidence must bind their own exact inputs and outputs.

The rehearsal-report correction has separate inert controls against the actual `fold_maps` body. The canonical empty-list report completes its mapping return; missing, false, nonempty and other-type declarations refuse. The seven gate names/statuses, five tool roles and source/manifest bindings retain focused coverage. Earlier counts are retained component evidence, not a claim that those suites were rerun for this change.
