## Answers
(a) Opening the base. RUN never opens a prior base; it builds one in-process: catalog created fresh at `<output>/compact-checkpoint/interval-catalog.json` (RUN:816-821) under the historical workflow_id (RUN:876-877); no head selection, the head is the migrated root it just published (RUN:638), sealed and promoted (RUN:643), reopened by `open_migrated` (RUN:648). SHA pins: original `database_sha256` (RUN:866, re-hashed :987,:1000); profile SHA as producer_identity and native source digest as runtime_identity (RUN:878); historical and current manifest SHAs (RUN:524-526); driver SHA (RUN:835); preparation and policy pins (RUN:353-360); final catalog SHA and member inventory (RUN:988-990).
    RO opens a hash-checked copy of the catalog named in the producer's run.json: run.json pinned by `--producer-receipt-sha256` (RO:616); catalog and every member re-hashed (RO:622 -> :548-552) with `checkpoint_sha256 == catalog_sha256` (RO:395); copies bound to their SHAs (RO:575-578); file hash == pin before `open_catalog` (RO:689), `store_set.catalog_digest == pin` after (RO:691); head = whatever `open_migrated` reaches by walking the chain (RO:890), then required equal to `completed['head_key']` with `parent_key == root['key']` (RO:762-763); `source_proof == sources.verify()` (RO:632). Contrast, ordinary run B: `open_catalog(<store_directory>/interval-catalog.json)` (F:705), `require_promoted_root` (F:707), `start_next_interval` (F:755), `Workflow.open` + ROOT_IDENTITY (FD:201-209).
(b) Trusted from the predecessor. Only RO consumes a predecessor receipt; RUN trusts none (it re-derives from the pinned original). RO takes run.json (SHA-pinned) and re-derives or compares: published_root {workflow_id, root_key, root_metadata_sha256, sequence, inspect, preparation_ids, execution_provenance, store limits/compression}, migrated_base (whole record), initial_workload, completed_endpoint {head_key, root_metadata, ids, array_records}, continuation, record_identities, compact_storage {catalog, catalog_sha256, files}. Taken at face value (shape and consistency only): status, errors, final_reserved_bytes, profile_sha256, pid, supervisor.pid, previous_endpoint (only head/intervals/funding_id, RO:352-355), compact_retained_*. Contrast: run B trusts run A's runner record, sealed record, reader verdict and the accepted-catalog head (F:392-405), read with no external pin; they cross-bind by SHA and only the catalog entry anchors them.
(c) Narrowest attachment. One gate at the start of `_advance_checked` (RUN:744-748), replacing the base test: it is the only production path (RUN:934) and already holds `workflow`, `store`, `before`, `parent=dict(workflow._head)` and `root_bytes` before `fence()` and the driver (RUN:752-756). It would compare the opened head with the predecessor's sealed records (runner, sealed, verdict, adopted for interval N-1, chained back to the root) and refuse on any difference, no fallback: catalog entry (interval, filename, file_sha256, logical_seal, producer/runtime identity), head SegmentRef, workflow_id, parent_digest chain, accepted catalog digest. Twins: D:89-106 (the existing 'refuse before any physical work' cluster) and, reader side, `validate_migrated_lineage` (RO:435) fed by `producer_inputs` (RO:612). Precedents: `require_promoted_root` (F:386-405, called F:707 right after `open_catalog`) and G's pinned `open_pending` (G:511: catalog digest, file SHA, logical seal, head, identities).
