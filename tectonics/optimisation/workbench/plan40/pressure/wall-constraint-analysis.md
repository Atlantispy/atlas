## Exact local CSE proof and proposed controls

This batch changes no algebraic association. `O._dot` is the exact ordered `sum((x*y for x,y in zip(a,b)), Fraction(0))`; `O._cross` is three exact two-product differences. Its arguments are internal tuple/list rational points issued by the integrator, not user-defined stateful iterators.

1. C `_triangle`: bind `nearest = tuple(v+t*w for v,w in zip(x,d))` once, then call `O._dot(nearest, nearest)`. The old expression creates equal tuples twice. For the three edges of each triangle this saves nine rational multiplications and nine additions plus three tuple constructions, while keeping the identical dot product and min order. It does not remove the already-evaluated zero-length edge fallback.
2. C `_radial_linear_mean`: bind each `offset = _minus(p, centre)` once before its squared norm. For three points this saves nine subtractions and three tuple constructions. Preserve the outer sum/divide and the original centre, radius, variance, remainder and bound expressions.
3. P `_cone_status`: compute `edge_normal = O._cross(a,b)` once inside the edge loop, then dot it against each point. For three points this saves two crosses per visited cone edge: twelve rational multiplications and six subtractions. The min/max and early return stay in their original places. Empty cone still returns 1; partially/fully negative contact remains distinguished. This has no benefit for empty native cones, and does not imply every pressure call uses the general branch.

Operation counts are source-derived, not timed. No selected operand-width histogram was produced by this subtask; use representative profile widths if subsequently supplied and do not substitute arbitrarily large synthetic rationals.

The proposed bounded exactness controls can load only the selected helper AST definitions with exact Fraction operands (no workers/native build): compare complete results and exception class for nonempty/empty cones, strict outside/inside/on-edge/mixed contact, zero/negative/large dyadic and non-dyadic coordinates, repeated triangle vertices, positive and zero minimum radius, nonzero `rc`, and a few actual fixture ray/triangle values if already available. Instrument only the named primitive operation counts to establish the claimed elimination; timing is unnecessary to prove this mechanism. For `_radial_linear_mean`, centre-at-zero and radial lower-bound zero should preserve the same failure instead of being silently skipped. For `_triangle`, preserve exact square-root enclosure and first-equal longest-edge choices through the existing unchanged caller. These controls establish local feasibility only; later production implementation still needs selected consumer exact-record checks and refusal/accounting controls.

The local live-value set is no broader than one formerly duplicated vector plus its consumer. Existing `V._work` guards include actual operand widths and reserve `65536 + 128*bits + 256*len(values) + 256*pairs` before yielding Fractions. Keep those calls and their values unchanged in a minimal batch. Any broader cache outliving the call needs an explicit separate lifetime charge; saved arithmetic is not permission to weaken admissions or cancellation.

## Boundary conclusions

The strongest non-jet opportunity is a small, deterministic removal of literal repeated vector work. The larger obvious proposals—wall preparation, raw constraint sharing, unique radial columns, exact zero anomaly and per-face polynomial reuse—are already present. New cross-wall/cache designs must not be counted as uncovered free wins. Broad plane/constraint preparation is not implementation-ready until its immutable scope and refusal-preserving charge design are explicit; the present source establishes both a repeated-work mechanism and the reason a naive eager cache is not equivalent.

No external research is needed to establish these source identities and exact arithmetic equivalences. No native method status changed in this source examination.
